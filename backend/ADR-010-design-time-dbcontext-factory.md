# ADR-010: Design-time DbContext factory for EF migrations under Aspire

## Status
Accepted — 2026-07-13

## Context
Aspire orchestrates entries-api and media-api at runtime, injecting connection strings via environment variables. The `dotnet ef migrations add` tool runs
outside Aspire — it tries to bootstrap the API's Program.cs to build a service provider, but the connection string comes from Aspire's runtime, not from
static configuration.

Two paths for the tool:
1. Bootstrap the startup project — fails without Aspire because the connection string is null
2. Use an `IDesignTimeDbContextFactory<T>` — an officially supported EF Core escape hatch for design-time DbContext construction

## Decision
Provide an `IDesignTimeDbContextFactory<T>` in each Infrastructure project. The factory constructs a DbContext with a placeholder connection string that
is only ever used for model building, never for connecting:

```csharp
public sealed class DesignTimeTriplogEntriesDbContextFactory
    : IDesignTimeDbContextFactory<TriplogEntriesDbContext>
{
    public TriplogEntriesDbContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<TriplogEntriesDbContext>()
            .UseNpgsql("Host=localhost;Database=entries;Username=postgres;Password=postgres")
            .UseSnakeCaseNamingConvention()
            .Options;

        return new TriplogEntriesDbContext(options);
    }
}
```

Migrations can now be generated by running dotnet ef migrations add from within the Infrastructure project without needing Aspire running or a real
connection string. Migration files land in Persistence/Migrations/.

## Consequences
Positive:

- Migrations work without booting Aspire
- Migration tooling isolated from API startup — any Program.cs issues don't block schema work
- Officially supported EF Core pattern (documented at https://learn.microsoft.com/en-us/ef/core/cli/dbcontext-creation)
- Portfolio-friendly — a reviewer can generate a fresh migration with one command from the Infrastructure project

Negative:
- Placeholder connection string doesn't connect anywhere; if migrations ever needed real DB access at design time, we'd need a real connection
- Configuration duplicated between factory and Infrastructure DI (both call UseNpgsql + UseSnakeCaseNamingConvention) — a small extension method
could consolidate but adds ceremony for portfolio scope

Neutral:
- Migrations don't actually connect at design time; EF Core only builds the model and diffs against the last snapshot. The placeholder string is never
used to open a connection.

## Alternatives considered
- Fallback connection string in appsettings.json — rejected because the API would try to connect to that literal string when run outside Aspire,
creating a confusing failure mode
- Environment variable set before every dotnet ef invocation — rejected as fragile and non-obvious; breaks in CI without explicit setup
- Run dotnet ef with --startup-project pointing at the API — works but bootstraps the full API pipeline, coupling migration tooling to
unrelated startup concerns
